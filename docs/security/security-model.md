# Модель доступа и защиты данных

Документ описывает проектные меры, а не утверждение о соблюдении всех правовых требований. Разрешения на публикацию, состав персональных данных, провайдера ИИ и условия обработки подтверждает заказчик до запуска.

## Границы доверия

- Браузер посетителя не определяет права; все фильтры, ID, размеры и статусы валидирует сервер.
- Сотрудник действует в пределах permission и branch scope. Администратор филиала не меняет ресурсы другого филиала через подмену ID.
- Приватный репозиторий исследования не является публичной базой знаний. Сырой импорт, отзывы и сохранённые HTML нельзя отправлять модели целиком.
- Внешняя модель получает только разрешённый минимальный контекст. Документы могут содержать вредоносные инструкции: они не дают модели полномочий и не меняют системные правила.
- Файловый URL, поисковый chunk, превью и старая цитата не обходят актуальные права.

## Раздельные решения

1. **Публикация:** выбранная языковая версия одобрена и доступна.
2. **Метаданные:** какие поля карточки разрешены публично.
3. **Файл:** разрешён ли просмотр/скачивание конкретной копии.
4. **OCR/ИИ:** разрешён ли проверенный текст и выбранный канал его обработки.

При сомнении ресурс остаётся внутренним; `unknown` не равно `open`. Публичная карточка закрытого документа использует только разрешённое описание, не скрытый текст скана.

## Начальные роли из ТЗ

| Роль | Предлагаемая область |
|---|---|
| Главный администратор | Все модули и назначение полномочий |
| Администратор сайта | Контент, пользователи и настройки в предоставленных границах |
| Редактор | Подготовка и публикация информационных материалов согласно разрешениям |
| Сотрудник архива | Каталог и материалы в назначенной области |
| Администратор филиала | Информация и материалы своего филиала |
| Модератор | Проверка, возврат и одобрение редакций |
| Аналитик | Обезличенные показатели и отчёты, без прав редактирования |

Это начальные назначения, а не жёстко зашитые роли. Сочетание редактирования/одобрения и возможность проверять собственную работу нужно определить с заказчиком. Любое изменение прав записывается в аудит.

## Минимальные технические меры

HTTPS; параметризованные SQL-запросы; экранирование и очистка HTML; CSRF-защита для cookie-сессий; безопасные cookie; хеширование паролей штатным проверенным механизмом; rate limit и idle timeout; недоступность admin для анонимных запросов. Ошибки содержат безопасный код, а подробности доступны сотруднику в журнале.

Загрузка: ограничения размера и типа по содержимому, случайный storage_key, карантин, антивирусная/форматная проверка, отказ от выполнения макросов/HTML, отдельные производные файлы. SVG/HTML из внешних источников не считать безопасной картинкой. Перед экспортом CSV исключить исполнение формул текстовыми ячейками/безопасным форматом.

Robots.txt и закрытие кнопки в UI не заменяют авторизацию. Общий доступ к bucket не используется для закрытых копий. Не выводить приватные storage_key и контакты из feedback в публичный API.

## Хранение и удаление

Сроки хранения чата, контактов обратной связи, аудита и резервных копий — отдельные настройки, согласуемые перед запуском. Аналитика использует агрегаты без постоянного пользовательского профиля. Отзывы не становятся официальными обращениями. Геолокация запрашивается только для маршрута и не сохраняется в БД сайта без отдельной необходимости/основания.

Проверять восстановление БД вместе с файлами. При удалении/отзыве источника обработать индекс, кэш, цитаты и сохранённые ответы. Перед публичным выпуском провести негативные тесты из [плана](../testing/README.md).
